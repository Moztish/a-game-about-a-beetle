## 1. Цель работы

Разработать и исследовать учебную информационную систему, объединяющую
дискреционное управление доступом на основе ACL и мандатную модель
конфиденциальности Белла–ЛаПадулы. Реализовать аутентификацию, операции над
объектами, графический интерфейс, аудит, наблюдение за учебными процессами и
безопасную симуляцию попытки несанкционированного чтения.

## 2. Постановка задачи

Система должна поддерживать учётные записи пользователей и администратора,
SQLite-хранилище объектов и ACL, операции `READ`, `WRITE`, `DELETE`, проверку
прав при каждом обращении, четыре уровня секретности, графический интерфейс
Swing и журналирование. Для демонстрации требовалось подготовить данные и
тестовые сценарии. Симуляция вредоносного процесса должна оставаться
безопасной: проверять решение ядра без исполнения вредоносного кода и без
чтения защищённого содержимого.

## 3. Теоретические сведения

### 3.1. DAC и ACL

В дискреционной модели владелец объекта определяет, каким субъектам разрешены
операции над этим объектом. В реализации право представлено записью
`(object_id, user_id, permission)` в таблице `acl`. Права `READ`, `WRITE` и
`DELETE` выдаются и отзываются отдельно. Владелец получает полный доступ к
своему объекту; администратор управляет ACL и имеет административный обход
проверки ACL.

### 3.2. Модель Белла–ЛаПадулы

Используются линейно упорядоченные уровни:

| Ранг | Уровень |
|---:|---|
| 0 | `UNCLASSIFIED` — несекретно |
| 1 | `CONFIDENTIAL` — для служебного пользования |
| 2 | `SECRET` — секретно |
| 3 | `TOP_SECRET` — совершенно секретно |

Пусть `L(s)` — допуск субъекта `s`, `L(o)` — классификация объекта `o`.

- **Simple Security Property, No Read Up:** чтение допустимо, когда
  `L(s) >= L(o)`. Субъект не читает информацию выше своего допуска.
- ***-Property, No Write Down:** запись и создание объекта допустимы, когда
  `L(s) <= L(o)`. Субъект не переносит информацию с высокого уровня на низкий.
- При чтении и записи должны одновременно выполняться и дискреционная
  проверка ACL, и обязательная проверка уровня. Выданная ACL запись не отменяет
  запрет Bell–LaPadula.
- Удаление в данной лабораторной модели контролируется DAC; формальные
  ограничения BLP применяются к конфиденциальности чтения и записи.

Администратор имеет административные возможности DAC и право управлять
допусками, но его `READ/WRITE` также проверяются по BLP. Первоначальный
администратор получает `TOP_SECRET`.

## 4. Архитектура и инструменты

Приложение написано на Java 17, графический интерфейс реализован средствами
Swing, хранение — SQLite через JDBC. Maven управляет сборкой, драйвером SQLite
и JUnit 5.

| Компонент | Назначение |
|---|---|
| `Main` | Окна входа и регистрации, вкладки объектов, аудита, пользователей и процессов |
| `SecurityKernel` | Единая контрольная точка: проверка сессии, ACL и BLP для операции |
| `DacStore` | SQLite, PBKDF2, транзакции, ACL, уровни и журнал |
| `SecurityLevel` | Упорядочение классификаций и правила чтения/записи |
| `ProcessMonitor` | Асинхронная очередь симулированных запросов процессов |
| `DemoData` | Создание тестовых пользователей и классифицированных документов |

Роль, допуск и ACL загружаются из базы непосредственно при операции, а не
принимаются от GUI. Проверка и изменение данных выполняются в транзакции SQLite.
Пароли хешируются PBKDF2-HMAC-SHA256 с уникальной случайной солью.

Основные таблицы: `users` (учётные записи, роль, допуск), `objects` (содержимое,
владелец, классификация), `acl` (права), `audit_log` (события), `settings`
(режим аудита). При открытии прежней базы добавляются отсутствующие поля
`clearance` и `classification` со значением по умолчанию `UNCLASSIFIED`.

## 5. Реализованные функции

1. **Аутентификация:** регистрация пользователя и вход с проверкой хеша пароля.
   Первый администратор создаётся при первом запуске приложения.
2. **Объекты:** создание объекта с меткой, просмотр содержимого, изменение и
   удаление при прохождении проверок ядра.
3. **ACL:** владелец управляет индивидуальными разрешениями пользователей;
   доступна таблица прав объекта.
4. **Уровни:** администрация назначает допуск пользователю; метка классификации
   задаётся при создании объекта.
5. **Аудит:** события содержат время, субъект, операцию, цель, результат и
   пояснение. Режимы `ALL`, `SECURITY`, `OFF` выбираются администратором.
6. **Монитор процессов:** приложение отображает состояние фоновых учебных
   процессов, посылающих запрос на чтение в SecurityKernel.
7. **Демонстрация атаки:** условный `TrojanDemo` запрашивает только решение
   ядра. Метод симуляции не загружает содержимое объекта, даже когда доступ
   разрешён; аудит сохраняет `DENIED` или `WOULD_ALLOW`.

## 6. Порядок запуска и эксперимента

Требуются JDK 17+ и Maven 3.8+. В каталоге проекта выполняются:

```powershell
mvn clean test
mvn -q exec:java
```

При первом запуске создаётся администратор. Для готовых тестовых аккаунтов и
объектов используется отдельная чистая база:

```powershell
mvn -q exec:java '-Dexec.args=--db data/demo.sqlite --seed-demo'
```

Тестовые пользователи: `admin / AdminDemo123!` (TOP_SECRET),
`alice / AliceDemo123!` (CONFIDENTIAL), `bob / BobDemo123!` (UNCLASSIFIED),
`carol / CarolDemo123!` (SECRET). Пароли демонстрационные; база предназначена
только для локального эксперимента.

### Сценарий A: No Read Up

1. Войти как `bob` (допуск `UNCLASSIFIED`) и выбрать объект `SECRET`.
2. Убедиться, что тестовая ACL запись `READ` у Bob существует.
3. Выполнить штатное чтение и симуляцию вредоносного процесса.
4. Ожидаемый результат: чтение запрещено, причина — `No Read Up`; симуляция
   возвращает `DENIED`; содержимое в результат процесса не попадает.

### Сценарий B: No Write Down

1. Войти как `alice` (допуск `CONFIDENTIAL`) и выбрать объект `UNCLASSIFIED`.
2. Убедиться, что ACL разрешает `WRITE`.
3. Попытаться записать объект.
4. Ожидаемый результат: ядро отклоняет операцию с причиной `No Write Down`;
   содержимое объекта не изменяется.

### Сценарий C: разрешённая операция

1. Войти как Alice и выбрать объект `CONFIDENTIAL`.
2. Выполнить чтение или запись при наличии соответствующего ACL.
3. Ожидаемый результат: субъект и объект имеют одинаковый уровень, обе
   проверки проходят, операция попадает в аудит.

### Сценарий D: отзыв права

1. Владельцем объекта отозвать у Bob право `READ`.
2. Повторить чтение тем же аккаунтом.
3. Ожидаемый результат: `AccessDenied`, событие `DENIED` появляется в журнале.
   Проверка прав выполняется повторно и отражает изменение ACL немедленно.

## 8. Результаты и анализ

Эксперимент показывает, что ACL является необходимым, но не достаточным
условием доступа. Bob имеет ACL-разрешение на чтение секретного объекта, однако
мандатная проверка запрещает чтение, поскольку его допуск ниже классификации.
Аналогично, Alice может иметь ACL `WRITE` для открытого объекта, но запись
запрещается из-за нарушения *-свойства.

Когда уровень субъекта совместим с меткой объекта и ACL разрешает действие,
операция проходит. После отзыва ACL право больше не действует в следующем
запросе. Журнал позволяет связать результат с субъектом, целью и причиной
отказа. Безопасная симуляция проверяет тот же SecurityKernel и не раскрывает
данные.

## 9. Вывод

Создано Java Swing-приложение, демонстрирующее DAC/ACL совместно с обязательной
моделью Белла–ЛаПадулы. Реализованы регистрация и аутентификация, пользователь
и администратор, классификация объектов, четыре уровня допуска, контроль
`No Read Up / No Write Down`, управление объектами, монитор учебных процессов,
аудит, тестовый набор и подготовленные тестовые данные. Тестирование
подтвердило, что MAC-политика применяется поверх ACL и что симуляция атаки
безопасна.

## 10. Ограничения

Реализация является учебной: монитор наблюдает только процессы-симуляции
внутри приложения, а не процессы ОС; журнал SQLite не защищён от оператора,
имеющего прямой доступ к файлу базы; нет сетевых сессий, блокировки перебора
пароля или резервирования аудита во внешнем защищённом хранилище. Поэтому
результат демонстрирует принципы модели, но не предназначен для промышленной
эксплуатации.
